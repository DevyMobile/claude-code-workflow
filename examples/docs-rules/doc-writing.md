# 문서 작성 규칙 (예시)

> AI와 사람이 같은 문서 저장소를 읽고 쓸 때 쓰는 규칙의 예시다.
> 프로젝트에 맞게 고쳐 쓴다.

## 원본은 마크다운 하나다

빌드 산출물(HTML 등)은 커밋하지 않는다. 문서를 고칠 때는 원본만 고친다.
산출물을 고치는 것은 다음 빌드에서 덮어써지므로 의미가 없다.

## frontmatter는 필수다

```yaml
---
title: 제목
status: draft          # draft | active | done | archived
owner: <이름>
area: <프로젝트 키>     # 목록을 프로젝트별로 묶는 기준
updated: 2026-01-01
---
```

`updated` 를 갱신하지 않은 수정은 하지 않는다. 이게 없으면 문서가 언제 기준인지 알 수 없다.

## 파일명

`YYYY-MM-슬러그.md`. 날짜를 앞에 두면 정렬만으로 최신순이 된다.
설계 문서(PRD)와 구현 문서(spec)는 **같은 파일명**을 써서 짝이 눈에 보이게 한다.

## 문서를 지우지 않는다

수명이 다한 문서는 `status: archived` 로 바꾼다. 지우면 그 문서를 참조하던 다른 문서가
깨지고, "왜 없어졌는지"를 아무도 답할 수 없다.

## 어디에 쓸지

| 쓰려는 내용 | 위치 |
|---|---|
| 무엇을 왜 만드는가, 성공 기준 | `prd/` |
| 어떻게 만드는가, 구조와 인터페이스 | `specs/` |
| 두 선택지 중 왜 이걸 골랐는가 (되돌리기 어려운 결정만) | `decisions/` |
| 앞으로 계속 지킬 기준 | `rules/` |
| 순서대로 따라 하는 절차 | `guides/` |

PRD에 구현 방법을 쓰지 않는다. 구현은 바뀌어도 PRD는 안 바뀌어야 한다.

## 결론을 위에 쓴다

배경부터 시작하지 않는다. 결론과 요약을 맨 위에 두고 근거를 아래에 둔다.

## 다이어그램

플로우와 분기는 텍스트 기반 다이어그램(mermaid)으로 그린다. ASCII 트리로 그리지 않는다.
항목 하나를 끼워 넣을 때 세로선을 손으로 다시 맞춰야 하기 때문이다.

- 노드 라벨은 따옴표로 감싼다
- 노드가 15개를 넘으면 쪼갠다
- 라벨은 짧게 쓰고, 조건 상세는 옆의 표에 적는다

## 시크릿

API 키, 접속 정보, 토큰, 고객 데이터는 문서에도 쓰지 않는다. 저장소에 들어가면 이력에
영구히 남는다. 필요하면 "비밀번호 관리자의 X 항목"처럼 위치만 가리킨다.

## 분량

화면 열 번을 넘게 스크롤하면 쪼갠다. 읽히지 않는 문서는 없는 문서와 같다.
